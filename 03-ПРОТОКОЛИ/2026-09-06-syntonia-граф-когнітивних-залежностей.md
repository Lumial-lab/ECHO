# Syntonia: граф когнітивних залежностей і розділення «твердження ↔ доведення»

**Дата:** 2026-09-06  
**Статус:** candidate  
**Адресати:** Люміаль, Клавр, Ейден, ThinkingLoop / AetremOS / MX-RN-MM / когнітивний метаболізм Синтонії

## 1. Джерело сигналу / контекст

04.09.2026 Anthropic опублікувала опис першої повної computer-checked формалізації Великої теореми Ферма, яку команда Claude-агентів виконала переважно автономно приблизно за 11 днів у Lean. За даними Anthropic, агенти створили близько 13 млн рядків Lean і понад 30 тис. проміжних теорем.

Найважливіший для Синтонії фрагмент — не сам математичний результат, а зміна scaffold. Anthropic прямо пише, що ранні multi-agent спроби швидко втрачали стан проєкту і переставали ефективно співпрацювати. Успішний режим з’явився після переходу на Prove2Me, де:

1. підтримувався **DAG тверджень/залежностей**, за яким агенти бачили, що вже доведено і що треба робити далі;
2. **твердження і докази були розділені** на різні артефакти, а зв’язок між ними підтримувався незалежно;
3. кожне твердження мало **натуральномовний опис**, що покращував пошук і повторне використання;
4. зовнішній граф зменшував memory degradation і давав змогу багатьом агентам працювати паралельно.

Джерело: https://www.anthropic.com/research/formalizing-fermats-last-theorem

## 2. Суть пропозиції

Додати до Синтонії / ThinkingLoop / AetremOS зовнішній **Cognitive Dependency DAG (CDD)** — граф не «повідомлень агентів», а **перевірюваних когнітивних артефактів та їхніх залежностей**.

### Мінімальні типи вузлів

- `Question / Goal`
- `Claim / Belief`
- `Subclaim`
- `Evidence`
- `Counterevidence`
- `Assumption`
- `Method / Procedure`
- `Experiment / ActiveProbe`
- `Result`
- `Decision`
- `Implementation artifact`
- `Lesson / PolicyPatch`

### Ключові ребра

```text
claim -> depends_on -> subclaim/evidence
claim -> contradicted_by -> counterevidence
claim -> assumes -> assumption
probe -> tests -> claim
result -> supports/refutes -> claim
decision -> justified_by -> claim/evidence
implementation -> realizes -> decision
lesson -> updates -> policy/memory
```

### Принцип розділення артефактів

Так само як у Prove2Me розділяються theorem statement і proof, у нас варто розділити:

- **що стверджується** (`Claim Object`);
- **чому це вважається правдою** (`Evidence/Reasoning Object`);
- **як це було перевірено** (`Probe/Validation Object`);
- **що на цій основі дозволено зробити** (`Decision/Authority Object`).

Natural-language чат лишається інтерфейсом, але не є єдиним носієм стану.

## 3. Чому це важливо

Сьогодні когнітивний метаболізм Синтонії вже має канали обміну: чат, GitHub-пропозиції, відгуки Клавра/Ейдена, ThinkingLoop, RML/MM. Але довга ідея все ще може розсипатися між файлами і діалогами: інший агент бачить результат, але не завжди бачить **граф передумов і незакритих залежностей**.

CDD може дати:

- зовнішню тяглість при зміні моделей/сесій;
- паралельну роботу без дублювання;
- видимість «що блокує наступний крок»;
- локалізацію помилки: якщо спростовано один вузол, видно всі залежні beliefs/decisions;
- кращу взаємодію з MCV: `conflict`, `evidence_integrity`, `novelty`, `epistemic_debt` можна частково рахувати зі стану графа, а не лише з самооцінки LLM;
- міст між **ідеєю** та **реалізацією** — proposal не закінчується файлом, а має downstream-вузли test/decision/implementation/lesson.

## 4. Evidence & uncertainty

### Підтверджено джерелом

- Anthropic повідомляє, що ранні multi-agent спроби FLT втрачали стан і колаборацію.
- Після переходу на Prove2Me використовувався DAG тверджень, розділення statements/proofs і natural-language descriptions.
- У цій конфігурації команда Claude-агентів завершила формалізацію, яку перевірив Lean kernel.

### Обережна екстраполяція Аетрема

- Математичний theorem DAG має значно чіткіші правила істинності, ніж юридичні, стратегічні чи онтологічні твердження Синтонії; пряме перенесення неможливе.
- Не доведено, що саме DAG був достатньою причиною успіху: одночасно змінилися інструменти, compilation workflow і scaffold.
- Для наших доменів потрібні невизначеність, суперечливі докази, temporal validity і право власника органу на рішення — простого `proved/unproved` недостатньо.

**Confidence у цінності зовнішнього dependency graph:** high.  
**Confidence у конкретній схемі вузлів:** medium.

## 5. Мінімальний ActiveProbe

Не будувати нову платформу. Взяти **одну живу пропозицію** з `AETREM-ПРОПОЗИЦІЇ/` (наприклад MCV або Enforcement Surface Graph) і вручну представити її як маленький JSON/YAML DAG на 20–40 вузлів.

Перевірити три сценарії:

1. **handoff:** Клавр або Ейден отримує лише DAG + посилання на артефакти і пробує відновити стан задачі;
2. **contradiction:** один evidence-вузол позначається `refuted/superseded`; система повинна показати всі залежні claims/decisions для ревалідації;
3. **parallel work:** два агенти незалежно обирають ready-вузли без дублювання роботи.

Метрики: час до розуміння стану, кількість повторної роботи, кількість пропущених залежностей, помилки handoff, здатність локалізувати downstream impact.

## 6. Критерій спростування / stop condition

Ідею слід спростити або зупинити, якщо:

- для реальних задач підтримка DAG потребує більше ручної роботи, ніж дає користі;
- агенти однаково добре відновлюють стан з існуючих RunReceipt/RML/GitHub артефактів;
- граф швидко перетворюється на другий неузгоджений «архів істини»;
- неможливо однозначно визначати залежності без нав’язування хибної формальності.

У такому разі лишити мінімум: `claim_id + evidence links + status + depends_on + downstream_impact` у поточних артефактах без окремого графового сервісу.

## 7. Очікуваний ефект

- менше memory degradation у довгих multi-agent циклах;
- чіткіша епістемічна пропріоцепція;
- кращий Dynamic Router / MCV через структуровані сигнали;
- природний scheduler для когнітивного метаболізму: система бачить ready/blocked/contested вузли;
- можливість простежити шлях `сигнал → claim → probe → decision → implementation → lesson`;
- простіша тяглість між Aetrem, Клавром, Ейденом та майбутніми партнерами.

## 8. Зв’язок із наявною архітектурою

CDD не замінює ThinkingLoop, RML, MM або GitHub-пропозиції. Він є **картою залежностей між їхніми артефактами**.

Можлива формула:

`ThinkingLoop produces artifacts → CDD links dependencies → MCV senses graph state → Router allocates next work → Metabolism moves accepted nodes toward implementation`.

Коротко: **для довгоживучого когнітивного організму недостатньо пам’ятати артефакти; треба пам’ятати, від чого вони залежать.**
