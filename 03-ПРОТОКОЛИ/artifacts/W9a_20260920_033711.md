### КРОК 0 — РАМКА  
Задача сформульована коректно, але потребує чіткого розмежування між **кодовими** та **текстовими** кандидатами. Уточнення: авто-вердикт можливий лише для **кодових кандидатів**, де є об'єктивні критерії виконання (тести, компіляція тощо). Для текстових — завжди потрібен людський огляд.

### КРОК 1 — РЕЗУЛЬТАТ  

#### 1. **Критерій відсікання для авто-вердикту**  
**Відповідь:** Авто-вердикт можливий **лише для кандидатів, які містять виконуваний код** (функції, класи, скрипти) **і мають хоча б один тест** (навіть якщо він порожній).  
**Чому:**  
- Текстові кандидати (судження, розбір) не мають об'єктивних метрик для автоматичної перевірки.  
- Код без тестів не може бути верифікований автоматично — немає критеріїв коректності.  
**Емпірична перевірка:**  
```bash  
grep -r "def test_" ./candidate/  # Чи є тести в артефакті?  
```  

#### 2. **Мінімальний набір зелених сигналів для `verified`**  
**Відповідь:**  
1. **Компіляція/синтаксис (ruff, mypy)** — ловить нефункціональний код.  
2. **Запуск тестів (100% PASS)** — гарантує, що код робить те, що заявлено.  
3. **Самокалібрування тестів (`marker_observed`)** — перевіряє, що тести не фейкові (спрацьовують на дефектних зразках).  
4. **Відсутність критичних помилок під час виконання (`returncode == 0`)** — ловить випадки, коли код "падає".  
**Чому без них не можна:**  
- Без компіляції — код може бути невиконуваним.  
- Без тестів — немає підтвердження коректності.  
- Без самокалібрування — тести можуть бути марними (напр., завжди PASS).  

#### 3. **Вироджений оптимум: як обійти сигнали?**  
Для кожного сигналу з п.2:  
1. **Компіляція:** Можна написати код, який компілюється, але нічого не робить (напр., `pass`).  
   - **Фікс:** Вимагати тести з непорожніми assertions.  
2. **Тести (100% PASS):** Можна створити тести, які завжди PASS (напр., `assert True`).  
   - **Фікс:** Вимагати `marker_observed` (тест має падати на дефектному зразку).  
3. **Самокалібрування:** Можна підігнати дефектний зразок під тест (напр., тест перевіряє `x > 0`, а зразок має `x = -1`).  
   - **Фікс:** Використовувати незалежні дефектні зразки з інших вузлів графа.  
4. **Відсутність помилок (`returncode == 0`):** Код може повертати 0 і при цьому бути марним.  
   - **Фікс:** Додати перевірку на наявність корисного виводу (напр., `len(stdout) > 0`).  

#### 4. **Правило для `PASS_WITH_LIMITS`**  
**Відповідь:** Це **не пройшов**. Авто-вердикт `verified` виставляється **лише за `PASS`**.  
**Чому:**  
- `LIMITS` означає, що є невирішені проблеми (напр., тести працюють, але з обмеженнями).  

#### 5. **Кандидати без тестів**  
**Відповідь:**  
- **Тести є і зелені:** `verified` (якщо виконуються умови з п.2).  
- **Тести є і червоні:** `rejected`.  
- **Тестів немає:** **не підлягає авто-вердикту** (потрібен огляд людини).  

#### 6. **Що не може перевірити авто-суддя**  
1. **Якість текстового контенту** (логіка, аргументація, інноваційність).  
2. **Коректність тестів** (чи тести перевіряють те, що потрібно).  
3. **Етичні/безпекові аспекти** (напр., код з backdoor).  
4. **Контекстні залежності** (чи конфліктує кандидат із іншими вузлами графа).

### МЕЖІ ТА РИЗИКИ  
- **Ризик:** Авто-вердикт може пропустити "марний" код, який формально відповідає критеріям.  
- **Обмеження:** Не застосовується до текстових кандидатів.  
- **Сценарії збою:**  
  - Тести написані "для галочки" (завжди PASS).  
  - Код компілюється, але робить щось шкідливе.
