КРОК 0 — РАМКА (Frame Shift)

Формулювання K3 «що саме отримує покупець і в якій структурі» — хибна рамка, бо змішує три різні системи координат:
1. Артефакт платформної доставки (що Gumroad фізично рендерить після оплати).
2. Семантичну структуру ядра (як влаштована Notion-сторінка після дублювання).
3. Транзакційні правові умови (EULA, waiver, повернення).

Попередні невдачі D195 довели, що ця конвалюцція породжує нерозв’язні суперечності: замість доставки Notion-лінка описується ZIP-дерево README.md/Templates/Sandbox/; замість перевіреного механізму повернення вигадується чекбокс; замість власної EULA пропонується самосуперечлива CC. Тому K3 неможливо закрити атомарно — потрібне розбиття.

Сильніша рамка: спершу визначити **Протокол доставки** (K3.1), потім описати **Ядро контенту** (K3.2) і **Правову обгортку** (K3.3), а вже на їхній основі — **Версіонування** (K3.4). Без цього порядку структура описуватиме хибний носій.

КРОК 2 — РЕЗУЛЬТАТ

1. Відповідь по суті  
   Вузол K3 у чинній формулюванні незакриваємий одним кроком. Попередні невдачі D195 показали, що відповідь без розділення доставки, ядра та права призводить до:  
   - ZIP-метафори для Notion-лінка;  
   - вигаданого механізму повернення без виміру платформи;  
   - самосуперечливої CC-NC замість EULA.  
   Тому K3 розбито на K3.1–K3.4. Непохитні обмеження, які вже діють: формат — Notion-шаблон (B1.6); ліцензія — власна EULA із забороною реселу та перерозповсюдження (не Creative Commons); оновлення — потребують мажорного версіонування та deadline підтримки.

2. Хід міркування  
   B1.6 зафіксував Notion-шаблон, отже «пакет» не може бути файловим архівом. Питання «що отримує покупець» має два шари: обгортка Gumroad і ядро Notion. Без визначення доставки (K3.1) неможливо описати структуру (K3.2): якщо покупець отримує PDF — логіка одна; якщо plaintext-лінк — потрібна вбудована інструкція. Ліцензія (K3.3) залежить від платформної реалізації (K5.3), інакше норма нездійсненна. Версіонування (K3.4) залежить від того, чи доставка статична (неможливо оновити) чи динамічна (ризик нескінченної підтримки). Ланцюг залежностей: K3.1 → K3.2; K3.1 + K5.3 → K3.3; K3.1 + K3.3 → K3.4.

3. Емпірична перевірка  
   - Для K3.1: мінімальний стенд — sandbox-акаунт Gumroad (free план) + окремий workspace Notion. Створити товар категорії Digital/Other, прикріпити Notion-сторінку з увімкненим Share → Allow duplicate. Зробити тестову покупку (або використати Gumroad Preview). Зафіксувати: що точно відображається на сторінці завантаження (файл, текстове поле, кнопка). Перевірити дублювання з іншого Notion-акаунта.  
   - Для K3.3: відкрити актуальні сторінки Gumroad Refund Policy і Terms of Service; знайти розділи про digital goods та права споживача. Зафіксувати три стани окремо: (i) чи цифровий товар автоматично non-refundable; (ii) чи є технічний UI для явної попередньої згоди покупця на втрату права відмови (waiver of withdrawal); (iii) чи механізм відсутній. Якщо сторінки недоступні або UI змінився — зафіксувати «не виміряно».  
   - Для K3.2: після K3.1 задублювати тестову сторінку на чистий акаунт; зафіксувати, чи переносяться databases, formulas, linked pages, чи потрібен ручний імпорт.  
   - Для K3.4: задокументувати, чи зміна вихідної Notion-сторінки впливає на уже продані дублікати (ні) та як Gumroad дозволяє надсилати оновлення (email/attachment).

4. Відверті межі й ризики  
   У мене немає доступу до Gumroad seller dashboard, до живого інтернету для скрейпингу політик, до Notion sharing logs та до права здійснювати платежі. Я не можу підтвердити поточну версію UI Gumroad чи точні URL сторінок політики. Тому я не стверджую, що Gumroad має або не має механізму waiver; не описую конкретних кроків дублювання Notion без емпірики; не називаю очікуваного виводу тестового стенду. Будь-яка спроба закрити K3 без проходження K3.1 повторить помилку D195: структура без доставки перетвориться на ZIP-абстракцію.

5. Сценарії збою рішення ДО впровадження  
   - Сценарій «Невідповідність доставки» (K3.1): Gumroad у режимі digital product дозволяє лише текстове поле з лінком, а не PDF. Тоді K3.2 мусить розраховувати на inline-інструкцію в самій Notion-сторінці, інакше новачок не знатиме, як дублювати → зростання refund-запитів.  
   - Сценарій «Непідтримуваний waiver» (K3.3): Gumroad не має UI для explicit prior consent. Тоді K5.3 вже передбачив chargeback-ризик (Сценарій Г); K3 без цього виміру означає, що EULA буде нездійсненною для EU-покупців.  
   - Сценарій «Broken duplication» (K3.2): Notion share-link із Allow duplicate не переносить певних integrations або large databases. Якщо ядро містить такі блоки, покупець отримає «зламаний» продукт; без pre-flight checklist і мажорної версії продавець застрягне в циклі ручної підтримки.  
   - Сценарій «Статична доставка без версіонування» (K3.1+K3.4): якщо Gumroad видає статичний PDF із лінком, оновлення Notion-джерела не поширюється на минулі покупці. Тоді опис товару/EULA мають чітко фіксувати «версія на момент покупки», інакше очікування безкоштовних оновлень призведе до скарг.
