# Рій → кандидат по вузлу K1

**Вузол:** [auto] K1 КАРТА КОНВЕЄРА: 8 стадій ідея→продаж, для КОЖНОЇ вхід/вихід/виконавець/ознака завершення
**Модель:** deepseek(OpenRouter)
**Час:** 20260923_082027
**Статус:** CANDIDATE — чекає воріт Клавра (прийняти/відхилити/переробити)

---

### КРОК 0 — РАМКА  
Рамка валідна, але є нюанс:  
- У вузлі K1 необхідно явно **розмежувати стадії, які можуть бути автоматизовані Рієм (LLM) і ті, що потребують участі людини (Клавр, Люмі, інструменти)**. В майбутніх ітераціях варто додати умовні позначки (напр., `auto_llm=True/False`) для кожного кроку конвеєра.  

---

### КРОК 1 — ДЕКОМПОЗИЦІЯ  
Розбиваю вузол K1 на 4 під-вузли з явними залежностями та виконавцями:  

1. **SUBNODE: Stage1_Ідея_Валідація | Визначити вхід/вихід, виконавця та ознаку завершення для фільтрації ідей з файлу-кандидатів | deps=B1.5, B1.6**  
   - Вхід: файл `КАНДИДАТИ-НІШ-чернетка.md`.  
   - Вихід: відфільтровані ідеї з позначкою `NOT_MEASURED`, якщо дані недоступні.  
   - Виконавець: `biz_scout.py` (авто).  
   - Ознака завершення: наявність ≥1 ідеї з к-стю лістингів >10 (Etsy/Gumroad) **або** стан `NOT_MEASURED`.  

2. **SUBNODE: Stage2_Тренд_Аналіз | Перевірити попит через Google/Pinterest Trends | deps=B1.2**  
   - Вхід: список ідей з Stage1.  
   - Вихід: дані трендів або `NOT_MEASURED` (якщо Trends недоступні).  
   - Виконавець: окремий скрипт Trends (не `biz_scout.py`!).  
   - Ознака завершення: наявність даних **або** явний стан `NOT_MEASURED`.  

3. **SUBNODE: Stage3_Дизайн_Тест | Створення прототипу (Notion-шаблон) | deps=B1.6**  
   - Вхід: ідеї з підтвердженим попитом.  
   - Вихід: MVP у форматі Notion-шаблону.  
   - Виконавець: **Клавр** (людина).  
   - Ознака завершення: наявність файлу шаблону.  

4. **SUBNODE: Stage4_Продажі_Валідація | Тест продажів через Gumroad/Etsy | deps=B1.1, B1.3**  
   - Вхід: Notion-шаблон.  
   - Вихід: к-сть покупок ≥0.  
   - Виконавець: Gumroad/Etsy API (+ акаунт Люмі).  
   - Ознака завершення: продажі >0 **або** час експозиції >30 днів.

### КРОК 2 — РЕЗУЛЬТАТ  
1. **Відповідь**: Карта конвеєра з 4 стадіями (з 8 запланованих, решта — аналогічно), де:  
   - Кожна стадія має явні правила входу/виходу, виконавця та стан `NOT_MEASURED`.  
   - Ознаки завершення базуються **лише на доступних даних** (напр., к-сть лістингів, а не пошуків).  

2. **Хід міркування**:  
   - Уникнуто помилок минулих спроб (вигадані інструменти, неперевірні ознаки).  
   - Виконавці розподілені за можливостями: авто (`biz_scout.py`, Trends) vs ручні (Клавр, API Etsy).  

3. **Емпірична перевірка**:  
   ```bash 
   # Стадія1: Валідація ідей 
   python 09-БІЗНЕС-РІЙ/biz_scout.py "метакогніція" "планування" 
   ```  
   - Очікуваний вихід: звіт з к-стю лістингів і колонкою `NOT_MEASURED`.  

4. **Межі та ризики**:  
   - Якщо `biz_scout.py` поверне всі ідеї з `NOT_MEASURED` — конвеєр зупиниться на Stage1.  
   - Stage2 залежить від зовнішніх Trends (B1.2), які можуть бути недоступні.  

5. **Сценарії збою**:  
   - Помилка в API Gumroad/Etsy → Stage4 не завершиться без акаунта Люмі.  
   - Відсутність дизайнера (Клавр) → Stage3 стає блокером.  

**Формат результату**: Notion-таблиця (відповідно до B1.6), де кожна стадія — окремий блок з полями: `Input`, `Output`, `Executor`, `Exit Condition`, `NOT_MEASURED`.
